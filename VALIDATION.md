# Проверка версии 0.5.0

2 ноября 2026. Python перешёл на фоновые задачи: python.run возвращает jobId, python.status — фазу, время, stdout/stderr, progress(...) и итог, python.cancel отменяет. Автоматические таймауты запуска и выполнения удалены. У низкоуровневого Runtime осталась возможность явного срока для диагностических тестов; агент вызывает его с null. Пауза цикла не прерывает начатый Worker, выключение режима агента прерывает его даже после паузы модели. Преждевременный task.finish возвращает ошибку инструмента, а не ложный итог.

37 групп основной проверки: настоящий прогресс и stdout до окончания кода; другой браузерный инструмент во время Python; отмена; явное обозначение потерянного Worker без повторного исполнения; отказ преждевременного finish; сохранение полного результата перед экспортом; восстановление выгрузки из IndexedDB, включая архивную задачу; отсутствие перезаписи новой задачи фоновым результатом. Владение файлами обновляется атомарно, чтобы параллельные чтения страниц и экспорт Python не теряли записи друг друга.

`python-startup.py`: отсутствующая готовность sandbox, синхронный отказ Worker, ошибка WASM и отмена возвращают диагностируемое состояние. Простой код не загружает wheels; pandas не загружает matplotlib. Реальный Pyodide проверен без instantiateStreaming и с MIME application/octet-stream. Выявлено поведение официального loader 0.27.7: ошибки WASM могут только логироваться и оставлять незавершённый promise. Обёртка стандартного WebAssembly API передаёт ошибку, а несовместимый streaming заменяет обычной инстанциацией тех же локальных байтов; vendor и CSP не изменялись.

`mobile-engine.py`: чат → фоновый Python → status → файл → финал; настройки закрыты. Отдельно проверена остановка бесконечного Python после того, как цикл модели уже поставлен на паузу, и продолжение без повторного вычисления. Видимая история обновляет одну запись Python, проверки status скрываются.

Это реальные Worker/WASM/OPFS и сохранённый DOM через тестовый транспорт Chrome API. Живой DeepSeek, установленное расширение и Titanium на устройстве недоступны. Точная причина сообщения на телефоне пользователя не подтверждена; воспроизводимые проблемы загрузки устранены и теперь видны отдельные этапы вместо общего таймаута.

## Методика и её пределы

Распакованные расширения запрещены политикой администратора установленного Chromium. Диагностический вызов Extensions.loadUnpacked ранее вернул: `Loading of unpacked extensions is disabled by the administrator`. Запрет не обходился.

Поэтому стенды используют HTTP loopback и транспорт Playwright вместо Chrome API установленного расширения. Код service-worker.js, executor.js, контроллера, DOM-адаптера и Python исполняется настоящим Chromium; программные вызовы вкладок и runtime доставляются тестовым мостом. CDP действительно выполняется браузером. File API/OPFS, IndexedDB, iframe, Worker, WASM и Python настоящие. Для sandbox используется CSP с теми же ограничениями, но локальные HTTP-ресурсы заменяют chrome-extension URL.

Это подтверждает логику маршрутизации, изоляцию Python и независимость от вкладки настроек в стенде. Это не подтверждает работу web_accessible_resources, CSP и API конкретного мобильного расширения. Отдельные 404 favicon и сбросы HTTP-соединения при принудительной отмене Worker — ожидаемое поведение тестовой среды.

Разработческие тесты воспроизводимы из tests/dev. Они требуют Python/Playwright только у разработчика. Для пользователя тесты tests/index.html запускаются внутри расширения без npm, системного Python или сервера.

## Оставшаяся ручная приёмка

1. Загрузка расширения в Titanium, проверка версии Chromium и отсутствия ошибок manifest/CSP.
2. На странице DeepSeek появляются только переключатель и настройки; диагностика видит исполнитель в iframe. Настройки закрываются, задача продолжается.
3. Выбор внутреннего хранилища, привязка элементов касаниями, сквозная задача в авторизованном чате и скачивание результата на телефон.
4. Проверка CDP; при отсутствии — стандартный transport с выданным доступом к сайтам. Некоторые сайты отклоняют программные события.
5. Признаки генерации/завершения, реальная CAPTCHA, вход и лимиты DeepSeek. CAPTCHA не обходится; неопределённые состояния должны приводить к паузе.
6. Перезапуск/выгрузка мобильного браузера, восстановление состояния и отсутствие повторного исполнения незавершённых действий.

На Android следует оставлять DeepSeek на экране. Исполнитель во вкладке чата не защищает от завершения приложения ОС, блокировки телефона или нехватки памяти. Полная совместимость Titanium и живого DeepSeek пока не заявляется.

Также пройдены chat-discovery.py, touch-ui.py и все 14 групп основной проверки (включая Python и сквозной сценарий). Прежние проверки живого DeepSeek/Titanium остаются непроведёнными.

## 0.2.5 — автоматическая навигация, новый запуск и скрытый протокол

Снята блокировка обычных query/hash URL. Запрещены credentials, вкладка модели и явные параметры авторизации. Открытие URL больше не запрашивает подтверждения. Ссылки, поиск GET и элементы раскрытия доступны автоматически; неподдерживаемые изменения сайта возвращают структурированную ошибку до dispatch, без вопроса и без неопределённой команды. Произвольные формы и кнопки не выполняются автоматически.

Новая задача архивирует предыдущую, включая pending/outbound, вместо блокировки старым состоянием. Это новый запуск, а не повтор незавершённой операции. Новые диалоги alert/confirm в чат-управлении заменены короткими неблокирующими сообщениями. Первичная выдача браузерных разрешений и CAPTCHA по-прежнему зависят от самого браузера/сервиса.

Служебные запросы и JSON-команды визуально скрыты с сохранением текста и DOM для адаптера; видны задача, описание шага и финальный summary. Обновление представления ограничено по частоте и работает во время генерации. Мастер привязки временно восстанавливает исходное представление элементов.

Пройдены 15 групп основной проверки, включая URL поиска и политику действий без подтверждения. mobile-engine.py проверяет запуск после старых pending/outbound без сброса, сохранность архива, отсутствие подтверждений, Python и остановку. touch-ui.py проверяет мастер при скрытых сообщениях. final-view.py проверяет скрытие протокола на втором пользовательском DOM, сохранение исходного текста и читаемый итог. Живая отправка DeepSeek/Titanium пока не проверена.


## 0.2.6 — автоматическая сверка и продолжение из чата

Добавлен recovery.js: после сбоя используются сохранённые результаты команд, проверяется хеш записанного файла и принадлежность вкладки команде открытия. Неподтверждённый исход становится ошибкой инструмента, а не общей блокировкой. Неизвестное взаимодействие не повторяется; его вкладка остаётся доступна для чтения. Python с потерянным результатом не перезапускается. Ошибки чтения имеют одну дополнительную попытку, действия с побочным эффектом не повторяются.

Перед записью пользовательского результата журналируется фактическое имя и ожидаемый хеш. Перед отправкой DeepSeek различаются prepared, inserted и send-uncertain. Доставка сверяется с последним пользовательским сообщением; уже отправленный запрос читается без нового клика. Недоступная кнопка не считается состоявшейся отправкой. Если пользователь отправил подготовленный текст вручную, проверка истории не позволяет автоматически отправить его ещё раз. При отсутствии доказательств отправки нет слепого повтора и требования ручного сброса в настройках.

Сообщение «продолжай» возобновляет текущую задачу в исходной беседе, в том числе остановленную. Переключение в другой чат не должно подхватить старую задачу. Переход от пустого чата к созданной после первой отправки беседе учитывается по URL и данным доставки.

Основные проверки расширены до 19 групп: хеш записи после сбоя, несовпадающий файл без перезаписи, восстановление вкладки по commandId, отсутствие повторного неизвестного клика, продолжение после ошибки Python, восстановление ответа DeepSeek без отправки и однократная отправка подготовленного черновика. Мобильный стенд проверяет «продолжай» после остановки Python с сохранением идентификатора задачи и без настроек. DOM-проверки выполнены на обезличенной фикстуре и пользовательском экспорте. Живые DeepSeek и Titanium остаются непроверенными.


## 0.2.7 — DOMContentLoaded и стабильность содержимого

Удалено ожидание tabs.status=complete. Новая page-readiness.js проверяет readyState, текст и геометрию содержимого в изолированном мире; одинаковый код используется через CDP и scripting. Пробы каждые 250 мс, около секунды стабильности, минимум 1,2 с наблюдения, бюджет 15 с. Изменение документа или URL сбрасывает стабильность. Шум от nav/header/footer/aside/time и явно размеченной рекламы исключён. Для snapshot/extract возвращается readiness; ожидание после действий не вызывает повтор самого действия. По таймауту данные помечены неполными, глобальной остановки нет.

fixtures/readiness.html/js имитируют поздний текст, последующий сдвиг блока, индикатор загрузки и непрерывные часы. tests/dev/page-readiness.py проверяет оба транспорта: не требуется window.load и завершение постороннего запроса; блокирующий скрипт задерживает DOMContentLoaded; после click ожидается новое содержимое; загрузка, пустой контент и непрерывные изменения дают разные причины таймаута; отмена завершает ожидание. DOM/геометрия и CDP настоящие, транспорт chrome API заменён стендом.

Ожидание не доказывает смысловую полноту ответа сайта: поздние данные без индикаторов могут появиться после стабильного окна. Цветовые анимации, canvas, iframe не анализируются. Проба ограничена 1200 узлами, 200 прямоугольниками и 80000 символами для хеша; ограничение явно отражается sampleLimited. Живой Titanium и установленное расширение в этой среде не проверены.


## 0.3.0 — план сбора, локальные входы Python, сохранность каждой страницы

Добавлены browser.inspect и browser.collect. Инспекция выдаёт ограниченную структуру DOM и кандидаты CSS-селекторов; сбор выполняет проверяемый план контейнера и полей. Произвольного JS, cookies, значений полей ввода и обработчиков событий в плане нет. Сбор ограничен исследованным блоком, URL и документом; после навигации старый inspection отклоняется. Скрытые элементы, script/meta/iframe и формы ввода исключаются. Пропущенные значения и ограничения объёма указаны в результате.

Captures сохраняет полный результат страницы и индекс одной IDB-транзакцией, затем экспортирует отдельный JSON в выбранное хранилище. Запись восстанавливается по журналу и хешу; пользовательский файл с совпавшим именем не перезаписывается. Очередь отложенного экспорта также обрабатывается при новой задаче без возврата к старой; одновременные flush не дублируют запись. Имена автоматически создаваемых файлов и подпапок безопасны для зарезервированных идентификаторов Windows (проверен CON). Результаты, Python-выходы и журналы новых задач изолированы в tasks/<taskId>/. Начатая запись результата не отменяется остановкой агента.

python.run принимает files=[{path,name}]; локальные копии передаются через MessageChannel в /inputs, Python получает inputs[name]. Папка пользователя не монтируется, её handle не попадает в Worker. Доступ разрешён для результатов задачи, явно названных или перечисленных через files.list файлов. Вход ограничен 20 файлами/10 МБ каждый/20 МБ суммарно; выход — 30 файлами/5 МБ каждый/20 МБ суммарно, символьные ссылки отклоняются.

26 групп основного стенда: настоящие DOM/CDP, Worker/Pyodide и File System Access через OPFS. Новый сквозной тест собирает две страницы, сохраняет план и хеш, останавливает и восстанавливает состояние, читает полные JSON-файлы в Python и пишет CSV. Маркер после обрезанного просмотра подтверждает, что Worker получает полный файл. Дополнительно проверены сохранение при stop во время записи, восстановление после сбоя выгрузки, отсутствие дубликатов, конфликт пользовательского файла, границы входных путей и размеров. page-readiness.py проверяет план через CDP и scripting, включая запрет старого inspection после навигации. Мобильный стенд и представление на пользовательском DeepSeek DOM пройдены.

Это не проверка новой цепочки в авторизованном живом DeepSeek. Реальный выбор папки Windows/macOS/Titanium в этой среде не проверен: тесты используют тот же интерфейс File System Access с OPFS, транспорт chrome API заменён стендом. При выборе внутреннего режима OPFS данные не становятся файлами в папке устройства автоматически; нужна папка через File System Access либо скачивание.


## 0.3.1 — переиспользование рабочих вкладок

browser.open использует последнюю подтверждённую рабочую вкладку по умолчанию; совпавший URL не перезагружается. Новая вкладка — только первая или newTab=true. Следующая задача перенимает рабочие вкладки предыдущей с проверкой старого владельца session storage и передачей новому идентификатору задачи. Вкладка модели, посторонние/закрытые вкладки и вкладки с неподтверждёнными взаимодействиями исключены.

Перед tabs.update сохраняются намерение перехода и фаза dispatching. Проба готовности не принимает содержимое предыдущего документа за новый результат. Восстановление не повторяет непроверенный переход и не выдаёт старую страницу как новую. requestedURL сохраняется в ответе вместе с фактическим URL.

27 групп основной проверки: повторное использование при новом URL, отсутствие перезагрузки того же URL, явная отдельная вкладка, передача следующей задаче, неизменность посторонней вкладки и сохранность ранее собранных файлов. Стенд page-readiness.py проверяет CDP и scripting, включая задержку начала навигации с видимой старой страницей. Реальная установка расширения и Titanium на устройстве остаются непроверенными.
